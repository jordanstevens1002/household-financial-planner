# Household Financial Planner

> [!IMPORTANT]
> Household Financial Planner produces estimates and projections for personal exploration only.
> Nothing generated by this software is financial, tax, legal, lending, accounting or investment
> advice, and results should not be used as a substitute for advice from a suitably qualified
> professional. The original designer is not a financial professional and has no formal financial
> background. Calculations can be incomplete, outdated or wrong; verify important decisions
> independently and use the software entirely at your own risk.

Household Financial Planner is an open-source, self-hosted application for understanding how a
small household's finances may change over time. It combines dated records, explicit assumptions,
planned events and reusable scenarios without presenting projections as historical facts.

Version 1.0.0 uses FastAPI and PostgreSQL for storage and calculations, with an importable Appsmith
Community Edition interface. Australia is included as an example of the provider architecture, not
as a hardcoded country assumption.

## Features

- multiple isolated households and household members;
- dated income, expenses and backend-calculated household cash flow;
- property positions, ownership interests, rental portions and multiple loans;
- repayment schedules, offsets, redraw, refinancing comparisons and loan goals;
- generic retirement accounts, contribution profiles and projections;
- observed, planned and projected events on a unified timeline;
- saved, inherited and template-based scenarios with comparisons;
- country-neutral tax, purchase and retirement provider registries;
- maintained ISO country and currency selectors; and
- a household dashboard showing current cash flow, property positions and upcoming events.

This project is designed for personal households managing a small number of properties. It is not
intended to be accounting software, a professional property-management platform or an enterprise
financial system.

## Requirements

- Docker Engine with Docker Compose;
- enough local resources to run PostgreSQL, FastAPI, Appsmith and the React preview; and
- an OpenID Connect provider for production authentication.

Python 3.14 is used inside the API container. Appsmith is pinned to the version in `.env.example`
so an upstream image update cannot silently change the committed application schema.

## Quick start

1. Clone the repository and create the local environment file:

   ```bash
   cp .env.example .env
   ```

2. Replace every placeholder password and OpenID Connect value in `.env`.

3. For local-only evaluation, you may explicitly set:

   ```dotenv
   ALLOW_DEVELOPMENT_AUTH=true
   ```

   Development authentication must never be enabled on an internet-accessible deployment.

4. Start the stack:

   ```bash
   docker compose up --build
   ```

5. Open:

   - Appsmith: `http://localhost:8080`
   - React v2 preview: `http://localhost:3000`
   - API documentation: `http://localhost:8000/docs`
   - API readiness: `http://localhost:8000/health/ready`

6. Import [`appsmith/household-financial-planner.json`](appsmith/household-financial-planner.json)
   into Appsmith by following the [Appsmith guide](appsmith/README.md).

No credentials, household IDs or financial values are included in the committed Appsmith export.

## Configuration

| Variable | Purpose |
| --- | --- |
| `POSTGRES_DB` | PostgreSQL database name |
| `POSTGRES_USER` | PostgreSQL user |
| `POSTGRES_PASSWORD` | PostgreSQL password; replace the example |
| `DATABASE_URL` | SQLAlchemy async PostgreSQL connection URL |
| `OIDC_ISSUER` | Expected token issuer |
| `OIDC_AUDIENCE` | Expected API audience |
| `OIDC_JWKS_URL` | JSON Web Key Set endpoint |
| `ALLOW_DEVELOPMENT_AUTH` | Enables explicit local development identities |
| `LOCAL_AUTH_BOOTSTRAP_TOKEN` | One-time secret required to create the first local administrator |
| `SESSION_COOKIE_SECURE` | Requires HTTPS for local-session cookies; disable only for local HTTP |
| `SESSION_IDLE_MINUTES` | Sliding local-session idle timeout; defaults to 60 minutes |
| `SESSION_ABSOLUTE_HOURS` | Maximum local-session lifetime; defaults to 12 hours |
| `LOGIN_MAX_ATTEMPTS` | Failed attempts before local login is temporarily blocked |
| `LOGIN_BLOCK_MINUTES` | Local-login blocking and attempt-window duration |
| `RESET_TOKEN_MINUTES` | Lifetime of an administrator-issued password reset link; defaults to 30 minutes |
| `TEMP_PASSWORD_HOURS` | Lifetime of a newly generated temporary password; defaults to 24 hours |
| `LOG_LEVEL` | `DEBUG`, `INFO`, `WARNING`, `ERROR` or `CRITICAL` |
| `LOG_FORMAT` | `json` or local-friendly `console` |
| `APPSMITH_VERSION` | Pinned Appsmith Community Edition image version |

Settings are loaded through `pydantic-settings`. API logs use `structlog`, and every API response
includes an `X-Request-ID` that is also attached to its request log.
During the React migration, operators can review the
[local authentication API](docs/local-authentication.md) before its frontend is available.

## Optional fictional demo data

Demo data is never loaded automatically. With the local stack running and development
authentication explicitly enabled, create the small fictional example using:

```bash
docker compose run --rm api python scripts/create_demo_data.py --confirm
```

The script is idempotent for its named demo household. Do not run it against a real deployment.

## Data, backups and upgrades

Financial data is stored in the PostgreSQL Docker volume and Appsmith configuration is stored in a
separate Appsmith volume. Read [Backup and restore](docs/backup-and-restore.md) before relying on a
deployment and [Upgrading](docs/upgrading.md) before changing versions.

The original migration chain through v1.0.0 is forward-only. From v1.0.0 onward, schema changes
must include a tested downgrade path to the preceding release unless an irreversible migration is
clearly documented before release. Always take a verified backup before upgrading.

## Development and tests

Build and run the complete Python 3.14 quality image:

```bash
docker build --target test -t household-financial-planner-api:test api
docker run --rm household-financial-planner-api:test
```

Regenerate and test the Appsmith export:

```bash
python3 appsmith/generate_app.py
python3 -m unittest discover -s appsmith/tests -v
```

The backend keeps financial calculations outside the frontend and tests household isolation,
dated behaviour, provider abstraction, API validation and calculation results. See
[Architecture principles](docs/architecture-principles.md), [Code organisation](docs/code-organisation.md)
and [Contributing](CONTRIBUTING.md).

The React replacement is being developed alongside Appsmith. Its setup and quality
commands are documented in [the frontend guide](frontend/README.md).

## Extending country-specific behaviour

The shared application does not select a provider from household currency or jurisdiction.
Installed providers are discovered through registries:

- [Adding a tax provider](docs/custom-tax-provider.md)
- [Adding a retirement provider](docs/custom-retirement-provider.md)
- [Adding a purchase-cost provider](docs/custom-purchase-provider.md)

Bundled Australian implementations are working examples with explicit assumptions and supported
dates. They are not official government calculators.

## Use of AI in development

AI coding tools were used throughout development to turn the project outline and review feedback
into small implementation branches. Each change was inspected through pull requests and exercised
with automated tests, Docker checks and manual Appsmith walkthroughs. Human review determined the
product direction, accepted or rejected behaviour, and identified defects for correction. AI output
should therefore be treated as assisted implementation, not evidence that the financial logic is
professionally certified.
